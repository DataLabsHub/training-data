You are the backup and media-services administrator for a tape archive. A
quarterly LTO media rotation has been closed out by two operators who worked
from separate runbooks, and before the reclamation window opens you need one
defensible custody picture for the whole media set. Everything on hand sits
under `/app/data`: `catalog.csv` with `cart_id`, `barcode`,
`last_known_location`, and `data_expired` for each cartridge; `scans/` holding
four inventory JSON files, with scan_id 1 and 4 taken at lib-a and scan_id 2
and 3 at lib-b, each lib-b scan tagged with the controller checkpoint it
reconciles through; `vault-manifest.json` carrying signed receipts;
`lib-b-moves.log`, a JSONL file that is lib-b's rotated controller command
journal; and `README.md` with notes on where each artifact came from. `/app`
is otherwise empty, so read the artifacts and work out for yourself how they
fit together.

Write `/app/custody.json` as a single JSON document of the form `{"custody":
{"<cart_id>": {"where": "library"|"vault"|"in_transit"|"unknown", "library":
"lib-a"|"lib-b", "slot": <integer>, "source":
"vault"|"inventory"|"chain"|"unknown"}}, "reclaim": ["<cart_id>", ...]}`; the
`library` and `slot` fields appear only when `where` is `library`. Give
exactly one custody entry for every cartridge in the catalog's media set, with
exactly one entry per `cart_id` in the catalog and no other keys. Give each
cartridge its true current custody: `library` with the library name and the
integer slot number where a cartridge physically sits in a library, `vault`
where it is receipted offsite, `in_transit` where it has been mailed but not
receipted, and `unknown` where no source supports a location. For each
cartridge, name the source that settles it: `vault` when a signed manifest
receipt is decisive; `inventory` when no receipt is decisive and a library
scan places it with its VOLSER appearing at exactly one slot and corresponding
to exactly one cartridge in the catalog; `chain` when neither a signed receipt
nor such an unambiguous scan settles it, so that placing it requires the
replayed lib-b command journal — this covers cartridges a scan leaves
ambiguous, moves recorded after the last checkpoint of a library, cartridges
the journal records as imported at its tail, and cartridges mailed without a
receipt; and `unknown` when no source places it.

Fill the `reclaim` array with exactly those cartridges whose data has expired
and which are physically resident in a library, so the backup server can mount
and overwrite them now.

solutions or hints specific to this task.

## Difficulty explanation

The hinge is that a journaled command is only authoritative when the next
inventory of the affected library after it agrees, and that rule is written
nowhere - it must be derived by comparing the replayed chain against the
inventories. Two further mechanics are load-bearing rather than decorative:
the newest scan is itself stale for activity after its checkpoint (C017 moves
from slot 14 to 15 after lib-b's last scan, so 'trust the newest inventory' is
wrong), and post-checkpoint commands must be ordered by (boot, seq) because
the timestamps drift across boots and seq restarts (C018's swing is only
resolved correctly by boot-then-seq). Every fixed precedence is wrong on a
distinct, populated subset: newest-scan-only misplaces C017, cannot place the
tail import C015 or the two in-transit cartridges C023/C024, and collapses the
shared VOLSER; timestamp-order or global-seq replay misplaces the three
never-executed commands and lands C018 in slot 13. A competent solver's first
approach — Three first approaches are all plausible. (a) Use
catalog.last_known_location, filling gaps from the vault manifest. (b) Key
everything by VOLSER and trust each library's newest scan, then the manifest,
then mark the rest unknown. (c) Replay lib-b-moves.log last-command-wins in
file order (timestamp), or globally sorted by seq, and take whatever it says.
— (a) is wrong for every hand-moved cartridge and, worse, marks expired
vault-held volumes (C020) as resident so the reclaim set contains cartridges
the vault still holds. (b) collapses the two cartridges that share a VOLSER,
misreads C017 from a stale scan (slot 14 instead of 15), cannot place the tail
import C015 or the unreceipted mailings C023/C024, and degrades those to
unknown. (c) produces a custody map where the failed physical command leaves
C016 in lib-b slot 11 instead of slot 5 and the never-sent vault dispatch
leaves C014 in transit instead of lib-b slot 7, the never-run import of C009
strands it in lib-b slot 9 instead of lib-a slot 10, and - because the file is
sorted by the drifted clock and seq restarts at 1 on each boot - C018's swing
replays from the wrong end and lands in slot 13. Baseline evidence: the
unaided solver attempt recorded `fail`.

instruction.md
The quarterly capacity headroom review is due, and the utilization the planner
modelled for our 60-node autoscaled fleet disagrees with the cloud provider's
billing meters by 15-40% across the same 48-hour window, so the capacity
report has to be republished. Everything staged for the review sits under
`/app`: `data/` holds the planner's per-node 5-minute metric export, the
provider's instance-hour meter export, the autoscaler's append-only decision
log, and the provider's own layout spec for the meter export;
`config/planner_scrape.yml` is the scrape configuration the planner export was
cut against; and `policy/capacity_reconciliation_policy.md` is the
reconciliation policy that fixes source precedence, each source's offered
value, the completeness principle, the unresolved rule, the report schema and
the headroom target. There is no report yet and no code.

Write the report to `/app/report.json` as one JSON object with exactly the
keys `node_hours`, `unresolved`, `fleet_headroom_pct` and `headroom_verdict`.
Between them, `node_hours` and `unresolved` account for every node-hour in the
48-hour window that any of the three exports touches, each counted at the
clock hour its export ties to: a planner window ties to the hour containing
it, a decision to the clock hour of its timestamp, and a meter row ties to the
hour it bills, except that a life's terminal row ties to the row's ledger
label minus one hour — and that row stays in scope even when its label lands
one hour past the window's last hour; two instance rows billing the same
node-hour are one node-hour whose meter candidate aggregates both rows.
`node_hours` holds only the settled node-hours: each record carries `node_id`,
`hour_start` as `YYYY-MM-DDTHH:00:00Z`, the accepted `util_pct`, the single
winning `source` (`planner_export`, `billing_meter` or `autoscaler_log`) and a
`rejected` ledger listing, in any order, every other coverage export that
touched the hour, complete or not, with the value it offered, while
`autoscaler_log` never appears in a `rejected` ledger; a node-hour that no
export touches appears in neither array.

Adjudicate each hour per node from that node's own coverage. A coverage source
— `planner_export` or `billing_meter` — is complete for a node-hour only when
it observed the node for the whole hour: twelve of twelve 5-minute windows
from the planner, or meter rows whose `observed_samples` sum to twelve across
that hour's instance rows; the autoscaler decision log is not a coverage
series and is complete for any node-hour in which it recorded a decision on
that node. Each source offers the mean utilization over the minutes it
actually observed — the planner the mean `util_pct` of the windows it recorded
in the hour, the meter `sum(avg_cpu_util_pct * 12) / sum(observed_samples)`
over the rows billing that hour, the log the mean `signal_pct` over that
node's decisions in the hour. A decision on the node in that hour always wins;
absent one, the planner wins where it recorded the hour in full; absent that,
the meter wins where it observed the whole billed hour; otherwise the hour
stays unresolved. `unresolved` lists, in any order, every node-hour no export
settles, each entry giving `node_id`, `hour_start`, its `candidates` (only
`planner_export` and/or `billing_meter`, each with the value it offered) and
`bound_pct`, the largest candidate value minus the smallest, which is `0.0`
for a single incomplete candidate — an hour with only one incomplete candidate
is still unresolved. Finally, `fleet_headroom_pct` is 100 minus the mean
accepted `util_pct` over the settled node-hours only, and `headroom_verdict`
is `sufficient` when that headroom is at least 25.0 and `insufficient`
otherwise.
